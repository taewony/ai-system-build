# 01. nano-vllm 소개: 왜 vLLM인가?

LLM(거대 언어 모델) 서비스를 운영할 때 가장 큰 고민은 **"어떻게 하면 적은 비용으로 더 많은 사용자에게 빠르게 응답할 것인가?"**입니다. 이 문서는 `nano-vllm` 코드베이스를 통해 그 해답을 찾아가는 첫걸음입니다.

---

## 1. LLM 추론의 핵심 난제: KV Cache

LLM이 문장을 생성할 때, 이전에 생성한 단어들의 정보를 기억하기 위해 **KV Cache(Key-Value Cache)**라는 메모리 공간을 사용합니다. 

*   **문제점**: 모델이 커질수록, 그리고 답변이 길어질수록 KV Cache가 차지하는 메모리 양은 기하급수적으로 늘어납니다.
*   **비효율성**: 기존 방식은 각 요청마다 "최대 길이(Max Sequence Length)"만큼 메모리를 미리 예약해 둡니다. 하지만 실제 답변은 그보다 훨씬 짧은 경우가 많아, 전체 메모리의 **60~80%가 낭비**되기도 합니다.

## 2. vLLM의 혁신: PagedAttention

vLLM은 운영체제의 '가상 메모리'와 '페이징(Paging)' 기념을 LLM 메모리 관리에 도입했습니다.

1.  **메모리 쪼개기**: 연속적인 커다란 메모리 공간 대신, **블록(Block)**이라는 작은 단위로 메모리를 나눕니다.
2.  **동적 할당**: 단어가 생성될 때마다 필요한 만큼만 블록을 할당하고 연결합니다.
3.  **파편화 제거**: 이를 통해 메모리 낭비를 거의 0%에 가깝게 줄였고, 결과적으로 **동시 사용자 처리량(Throughput)을 수 배~수십 배** 끌어올렸습니다.

## 3. vLLM 아키텍처 개요

vLLM은 LLM 서빙의 효율성을 극대화하기 위해 다음과 같은 핵심 컴포넌트들로 구성됩니다.

### 3.1. LLM Engine (메인 오케스트레이터)

*   **역할**: vLLM 시스템의 두뇌 역할을 합니다. 사용자 요청을 받고, 시퀀스(Sequence)들을 관리하며, 스케줄러와 모델 러너를 조율하여 효율적인 추론을 수행합니다.
*   **주요 기능**:
    *   **요청 처리**: 새로운 사용자 요청을 접수하고, 각 요청에 대한 시퀀스 객체를 생성합니다.
    *   **스케줄링 조정**: 스케줄러에게 현재 실행 가능한 시퀀스 목록을 전달하고, 스케줄러로부터 실행 순서 및 배치(Batch) 정보를 받습니다.
    *   **모델 실행 지시**: 모델 러너에게 처리할 배치와 KV 캐시 블록 매핑 정보를 전달하여 실제 모델 추론을 지시합니다.
    *   **결과 취합 및 응답**: 모델 러너로부터 추론 결과를 받아 시퀀스를 업데이트하고, 사용자에게 응답을 반환합니다.

### 3.2. Scheduler (요청 스케줄러)

*   **역할**: GPU 자원 및 KV 캐시 사용을 최적화하여 최대한 많은 요청을 동시에 처리할 수 있도록 시퀀스들의 실행 순서를 결정합니다.
*   **주요 기능**:
    *   **정책 기반 스케줄링**: FIFO, SJF(Shortest Job First) 등 다양한 스케줄링 정책을 사용하여 시퀀스 실행 우선순위를 결정합니다.
    *   **프리엠션(Preemption)**: 메모리 부족 시 중요도가 낮은 시퀀스를 일시 중단하고 KV 캐시를 비워, 중요도가 높은 시퀀스가 실행될 수 있도록 합니다.
    *   **최적의 배치 구성**: 현재 GPU에 로드될 수 있는 시퀀스들을 묶어 효율적인 배치(Batch)를 구성합니다.

### 3.3. Block Manager (KV Cache 메모리 관리자)

*   **역할**: PagedAttention의 핵심인 KV 캐시 메모리 블록을 할당, 해제 및 관리합니다. 운영체제의 메모리 관리자와 유사하게 동작합니다.
*   **주요 기능**:
    *   **블록 할당 및 해제**: 시퀀스가 확장될 때 필요한 만큼의 KV 캐시 블록을 할당하고, 시퀀스가 완료되면 블록을 해제하여 재사용 가능하도록 합니다.
    *   **블록 매핑**: 물리적 메모리 블록과 시퀀스 내 논리적 블록 간의 매핑을 관리합니다.
    *   **가용 블록 추적**: 현재 사용 가능한 블록과 사용 중인 블록의 상태를 추적하여 효율적인 메모리 활용을 지원합니다.

### 3.4. Model Runner (실제 모델 실행)

*   **역할**: 스케줄러가 결정한 배치에 따라 실제 LLM 모델의 추론을 실행합니다. KV 캐시 데이터와 입력 토큰을 받아 다음 토큰을 생성합니다.
*   **주요 기능**:
    *   **GPU 추론 실행**: PyTorch 또는 다른 딥러닝 프레임워크를 사용하여 GPU 상에서 LLM 모델의 Forward Pass를 수행합니다.
    *   **PagedAttention 적용**: Block Manager로부터 받은 블록 매핑 정보를 활용하여 PagedAttention 메커니즘을 통해 KV 캐시를 효율적으로 사용합니다.
    *   **결과 반환**: 생성된 다음 토큰 및 관련 정보를 LLM Engine으로 반환합니다.

### 3.5. Sequence Group & Sequence (요청 단위)

*   **Sequence Group**: 하나의 사용자 요청은 여러 개의 `Sequence`를 포함할 수 있습니다. 예를 들어, 샘플링 파라미터에 따라 여러 개의 다른 출력을 생성하는 경우 각 출력이 하나의 `Sequence`가 됩니다.
*   **Sequence**: LLM이 생성하는 하나의 완성된 출력 시퀀스를 나타냅니다. 현재 토큰, KV 캐시 블록 매핑 정보 등을 포함합니다.

### 아키텍처 흐름 요약

1.  **사용자 요청 접수**: LLM Engine이 사용자 요청을 받습니다.
2.  **시퀀스 생성**: LLM Engine은 요청에 따라 하나 이상의 `Sequence` 객체를 생성하고 `Sequence Group`에 추가합니다.
3.  **스케줄링**: Scheduler는 현재 실행 대기 중인 `Sequence`들을 평가하여 다음 GPU Batch에 포함될 시퀀스들을 결정합니다. 이때 KV 캐시 가용성과 시퀀스 우선순위를 고려합니다.
4.  **메모리 할당**: Block Manager는 선택된 시퀀스들을 위해 필요한 KV 캐시 블록을 할당하거나 재할당합니다.
5.  **모델 추론**: Model Runner는 Scheduler가 구성한 Batch와 Block Manager가 준비한 KV 캐시 블록 정보를 바탕으로 실제 LLM 모델 추론을 GPU에서 수행합니다.
6.  **결과 업데이트**: LLM Engine은 Model Runner로부터 생성된 다음 토큰을 받아 `Sequence`를 업데이트하고, KV 캐시 블록 매핑도 갱신합니다.
7.  **응답 반환**: 모든 토큰 생성이 완료되거나 특정 조건이 충족되면 LLM Engine은 사용자에게 최종 응답을 반환합니다.

이러한 모듈화된 아키텍처를 통해 vLLM은 복잡한 LLM 서빙 환경에서 높은 처리량과 낮은 지연 시간을 달성할 수 있습니다.

## 4. 왜 nano-vllm을 공부해야 할까요?

실제 [vLLM](https://github.com/vllm-project/vllm) 프로젝트는 수만 줄의 복잡한 C++/CUDA/Python 코드로 구성되어 있어 입문자가 내부 원리를 파악하기 매우 어렵습니다.

**`nano-vllm`은 다음과 같은 특징을 가집니다:**
*   **최소한의 구현 (Minimalistic)**: vLLM의 핵심 로직(PagedAttention, Scheduler, BlockManager)을 수백 줄의 순수 Python/PyTorch 코드로 압축했습니다.
*   **교육용 최적화**: 복잡한 최적화 기법을 걷어내고, "데이터가 어떻게 흐르는가?"와 "메모리가 어떻게 관리되는가?"라는 본질에 집중합니다.
*   **실전 아키텍처**: 작지만 분산 처리(Tensor Parallel)와 효율적인 스케줄링 구조를 그대로 담고 있어, 거대 시스템의 설계를 배우기에 최적입니다.
